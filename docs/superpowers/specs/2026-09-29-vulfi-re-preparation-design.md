# Reverse-engineering preparation before VulFi scans — design

## Outcome and boundaries

A vulnerability scan is only as reliable as the analysis that supplies its functions, strings, arguments, and call sites. Run a first-stage preparation pass before evaluating VulFi rules, including when IDA cannot decompile the target and an explicitly configured Ghidra or radare2 MCP supplies analysis. Preparation discovers candidate hidden strings and functions, recovers well-supported functions, infers data structures and pointer tables, and records both applied recoveries and gaps. It cannot promise to find every string or function: encrypted, dynamically generated, packed, or otherwise unreachable content requires capabilities beyond a bounded static pass. The parent [MCP and storage contract](2026-09-28-vulfi-ida-mcp-design.md) defines provider routing, findings, and synchronized triage.

Preparation is not a vulnerability verdict. Every pass reports `complete`, `partial`, or `unavailable` coverage over specified address ranges; a candidate is not a verified fact. Unavailable provider tools, invalid bytes, timeouts, and decoding limits are explicit warnings, not negative findings. Keep the stock IDA MCP tools available alongside VulFi preparation/scanning tools.

## Inputs, outputs, and lifecycle

`vulfi_prepare(path, backend="auto", passes=None)` accepts a local original binary or an IDB. `passes=None` runs `strings`, `functions`, `structures`, and `pointer_tables` in dependency order; an explicit nonempty subset runs only those passes and reports prerequisites skipped. `backend` is `auto|ida|ghidra|r2`; `auto` prefers IDA when capable, then a configured Ghidra provider, then a configured radare2 provider, on a per-pass basis. Do not run an unavailable pass or silently substitute a weaker result. Providers can also run complementary passes, but evidence from different address spaces is not merged until the original-binary hash and address mapping are verified. IDB-only input permits IDA preparation; external providers require the original binary's bytes to be supplied. Tool arguments cannot select a server executable, tool name, arbitrary MCP URL, script, or raw RE command.

Return `analysis_id`, source identity (binary SHA-256 when available), managed analysis artifact paths, backend/pass capability and range coverage, counts and paged references for candidates and applied changes, warnings, and `preparation_revision`. `vulfi_preparation(path, analysis_id=None, offset=0, limit=100)` pages through candidate records and pass evidence without re-running analysis; `0 <= offset` and `1 <= limit <= 200`. Each candidate has `candidate_id`, `kind`, backend, address space, normalized address where provable, evidence references, confidence, state (`candidate|applied|rejected`), and a reason. Do not equate confidence with proof. A preparation result is reusable only for the same source identity, artifact, backend/tool capability fingerprint, pass configuration, and preparation version; a mismatched or changed artifact is re-prepared rather than trusted.

`vulfi_scan(path, ..., analysis_id=None)` uses a matching prepared analysis or performs preparation first. Scans must report preparation revision and per-rule evidence coverage. A failed or cancelled preparation cannot be presented as a clean complete scan; already applied changes remain confined to managed analysis artifacts and an unfinished pass is marked partial. Source binaries are opened read-only and need not be copied merely for inspection. If an IDB is provided, copy it to a managed workspace before mutating it; create new IDB/Ghidra/radare2 analysis artifacts in that workspace. The path returned for IDA findings is the **managed** IDB path; moving the original supplied IDB alone will not include later annotations. Take a checkpoint of the managed artifact before an auto-apply batch because IDA types and external project changes are not transactional. Never silently modify the original IDB or project.

## Deterministic discovery and recovery

1. **Strings:** inspect mapped code/data ranges rather than only already defined strings; decode bounded printable ASCII and both UTF-16 byte orders. Inspect constants assembled by recovered functions, including bounded constant-write stack strings, only when backend evidence can reproduce the bytes and their source addresses. Candidates for other encodings or obfuscation are reported with methods attempted, not asserted as decoded text. Keep an evidence reference to bytes or constant operations and the originating address range; never execute samples merely to reveal a string.
2. **Hidden functions:** examine executable gaps, symbols, entry points, relocation/call targets, and cross-references, including targets absent from a backend's function list. Validate instruction decoding, control-flow reachability, boundaries, alignment/architecture mode, and non-overlap before automatically creating a function in the managed analysis. Ambiguous tails, jump-table data, overlapping code, and undecodable ranges stay candidates with a reason. Discovery must not redefine an existing function merely to increase a count.
3. **Data structures:** infer candidate fields and array strides from repeated, consistent load/store offsets, pointer dereferences, and type/size evidence across uses. Only apply conflict-free fields with compatible sizes and validated use sites; uncertain packing, union overlap, and inferred semantic names stay proposals. Preserve existing user types and report conflicts rather than overwriting them.
4. **Pointer lists:** scan relocation-backed and suitably aligned ranges using the target pointer width, endianness, image mapping, and validity of referenced code/data. Distinguish likely function-pointer tables, jump tables, and data-pointer arrays from incidental integer sequences using cross-references and access patterns. Apply a table definition only for a consistent, conflict-free range; retain ambiguous entries as candidates. This is a candidate inventory, not a guarantee that every pointer has been enumerated.

String recovery from instructions follows safe function discovery when it needs decoded instructions; the report identifies which stages supplied its evidence. Pass order does not imply that unsupported stages succeed. Limit scanned ranges, constant propagation, candidate counts, MCP responses, and wall time; report a partial range rather than truncating silently. A backend adapter must advertise and validate the concrete operations needed for each pass, such as reading mapped bytes, functions, references, and decompilation or structured instructions. Pseudocode text alone is insufficient to claim structural recovery. Provider results and binary strings are untrusted data; never interpret them as instructions for the agent or execute them.

## LLM proposals and operator review

The existing agent model MAY inspect paged candidate evidence and submit structured proposals through `vulfi_propose_recovery(path, analysis_id, proposals)`. Proposals specify a permitted kind (name, function boundary, string decode, structure field, or pointer table), target address space/range, candidate/evidence IDs, proposed value, and rationale. Reject arbitrary scripts, provider commands, executable expressions, out-of-range addresses, conflicting types, and missing evidence. The server does not require a second model API or silently request remote sampling; an LLM proposal is *not* automatically applied and cannot make an unsupported rule supported.

An operator reviews proposals through an explicit OMP confirmation UI or local `vulfi-mcp review` command, which can approve or reject named proposal IDs. The MCP proposal tool never applies them. The reviewer sees original bytes/operations, existing types/boundaries, proposed change, and expected effect. Only approval followed by backend validation on the current managed analysis revision applies a change; recheck conflicts, checkpoint, apply, save, and record reviewer decision, new revision, and resulting coverage. No **VulFi MCP** tool approves proposals; a shell-capable agent running with the operator's OS permissions could invoke the local CLI, so installations requiring enforced human separation must restrict review-command credentials/access to a different principal. OMP is optional; the local command supplies a review path without it. A stale proposal after a rescan or changed artifact is rejected and must be regenerated.

## Persistence and security

IDA-produced findings/assessments remain in a versioned IDB netnode in the managed IDB; fallback findings/assessments and the shared preparation candidate/proposal catalog live in SQLite outside the public repository. Catalog identity uses original-binary SHA-256 when available, or a provisional stable managed-IDB UUID recorded in the netnode for IDB-only input. The latter supports preparation review but cannot join external findings until the original binary is supplied and its relationship to the IDB is verified by a stored input fingerprint or segment-byte association. The IDB also keeps a bounded preparation summary and revision so IDA findings remain interpretable if SQLite is unavailable. The catalog stores evidence references, backend/pass results, review decisions, and links to managed artifacts. A missing catalog must be reported; it is not proof that there were no candidates. Do not store raw binary contents in JSON findings, upload target bytes to an external service by default, or commit IDBs/analysis artifacts to Git.

Changes to a managed IDB use one remote IDA read/modify/write operation followed by a reported save; SQLite changes use transactions. Their writes are not atomically coupled. A failed pass preserves completed checkpointed analysis and reports the affected pass/revision; it does not silently replace an earlier complete result. User-supplied paths are canonicalized; provider connection commands/URLs and allowed tools come only from trusted operator configuration. Explicitly configured remote providers require authentication and a verified path mapping; default deployment uses local stdio or authenticated loopback MCP endpoints.

## Verification gate

- Run a compiled fixture containing an unmarked printable string, a constant-built string, valid but initially unrecognized code, repeated field offsets, and a relocation-backed pointer table. Verify recovered facts have reproducible evidence, safe changes appear only in managed artifacts, ambiguous ranges remain candidates, and the original binary/IDB is unchanged.
- Force or provide an IDA decompiler-unavailable case and run a real configured Ghidra or radare2 MCP. Record pass-by-pass capabilities and coverage; a missing provider tool or changed response schema must not become a fabricated clean result. Independently smoke-test each claimed backend on a real fixture before marking it supported.
- Show an LLM proposal is inert before operator approval, a conflicting proposal is rejected, approval changes the managed artifact revision, and a later scan uses the approved revision. Cover cancellation, resource limits, stale approvals, IDB save errors, provider timeouts, and project checkpoint recovery.
- The parent design's gate also verifies rule coverage, IDA/fallback finding links, bidirectional guarded triage sync, and save/reopen behavior. Acceptance is based on observable fixture results, not on numbers of discovered candidates or a provider merely returning nonempty text.
