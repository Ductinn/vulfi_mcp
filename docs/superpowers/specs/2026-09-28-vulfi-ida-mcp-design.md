# VulFi tools across IDA and fallback RE MCPs — design

## Purpose and acceptance

Expose VulFi vulnerability analysis, agent-authored rules, reverse-engineering preparation, and per-finding triage through one agent-facing MCP that extends Hex-Rays' official IDA MCP. Keep its six stock tools and do not fork `ida-mcp` or install an IDA GUI plugin. Before scanning, discover hidden strings/functions, recover safe function boundaries, infer structures and pointer tables, and report evidence and gaps. When IDA cannot decompile or open the target, a configured Ghidra/radare2 MCP supplies supported preparation and rule evidence; unsupported rules are identified rather than declared clean. A reviewer can approve links between matching IDA and fallback findings; subsequent triage synchronizes across their separate stores with guarded recovery. An optional OMP extension shows preparation and triage without replacing native todos. This is a design, not a runnable implementation; see the [preparation specification](2026-09-29-vulfi-re-preparation-design.md).

This is a design-stage project with no product code yet. IDA GUI attachment, GUI chooser/menu reimplementation, migration of legacy VulFi netnode rows, arbitrary Python execution from rule input, automatic execution of provider scripts or arbitrary MCP tools, and a general taint-analysis engine are outside scope. No static pass can guarantee detection of every hidden string or function; encrypted or runtime-generated content is reported as a gap unless backed by reproducible evidence.

## Runtime architecture

A `vulfi-mcp` entry point imports the documented `tool` and `serve_stdio` API from `ida_mcp.mcp`, registers VulFi tools, and serves that **same** process-wide MCP server. The agent config points to `vulfi-mcp` instead of `ida-mcp stdio`; its six stock tools remain visible. The IDA adapter uses only exported `ida_nexus` APIs (`DatabaseHandle.open`, `RemoteModule` or `remote_ida`) and never accesses `ida_mcp.mcp.DATABASE_MANAGER`, derives an IDA runtime from stock MCP-local `instance_id`, or monkeypatches stock tools. The Python host also acts as an MCP **client** of explicitly configured, vetted Ghidra/radare2 providers. No generic provider tool passthrough or arbitrary server URL/command is accepted from an agent. Each VulFi tool takes a local binary or IDB `path`; the raw binary is required for non-IDA fallback. IDA leases and external MCP sessions are owned by their adapters and released after use; no VulFi GUI plugin or second agent-facing server is installed. JSON-native results cross all MCP/Nexus boundaries.

IDA-specific preparation/scanning uses a separate source-backed Python module inside the IDA worker, not an agent-generated `execute_python` string. IDAPython decompiler/ctree and disassembly APIs supply the evidence needed by capable stock rules; `ida-domain` is available alongside them. The host's restricted rule interpreter and provider adapters operate on typed evidence, not arbitrary pseudocode execution. No VulFi GUI object, wait-box, chooser, popup, or modal call enters the IDA scan path.

Runtime support: Python >=3.11, IDA >=9.4 with activated idalib for the IDA-backed path, and an IDA license with Hex-Rays support for rules requiring its decompiler. The same entry point still depends on the official IDA MCP installation even when a particular target uses Ghidra/radare2. Provider versions and tool schemas are pinned and integration-tested; an external provider is optional until a target needs it. The supported IDA deployment has no Nexus/IDA-MCP GUI provider plugin enabled: if one is present, Nexus may prefer its GUI instance and headless-only behavior is not guaranteed. Nexus attaches to compatible headless workers, rejects incompatible peers, and surfaces an unregistered GUI's IDB lock as `DatabaseBusyError`; do not copy a stale locked IDB or bypass its lock. For preparation, import raw binaries into managed projects and copy a saved, unlocked user IDB into a managed workspace before modifying it. Original supplied artifacts remain unchanged.

### Local idalib feasibility check (2026-09-28)

The existing official IDA MCP was smoke-tested against a disposable copy of `/bin/true`, not a user IDB. `open_database` reported `backend="idalib"` and `recovery="none"`; the worker ran Python 3.14.3 and ida-domain 0.5.1. IDA enumerated 126 x86-64 functions through both `db.functions.get_all()` and `idautils.Functions()`, `ida_hexrays.init_hexrays_plugin()` returned `True`, and `db.pseudocode.decompile()` returned pseudocode for `.init_proc`. Saving `.i64`, closing its lease, reopening that IDB in an idalib worker, and decompiling again succeeded. Both leases were released and the temporary files removed.

This proves headless import, analysis, decompilation, and IDB save/reopen on this machine for **ELF x86-64 only**. A GUI-provider plugin is installed locally but no GUI database was attached during the test; this check does **not** prove startup with the GUI provider uninstalled, other architectures' decompiler availability, custom VulFi tools, or the OMP extension. The release-gate end-to-end checks below still have to prove those behaviors.

## Technology and component boundaries

|---|---|---|
| Agent-facing MCP adapter | Python >=3.11 | Official `ida-mcp` `@tool`/`serve_stdio`, `ida-nexus` `DatabaseHandle`/`RemoteModule`, and explicitly locked `ida-domain`. Retain six official IDA tools; no second VulFi MCP server. |
| IDA analysis and preparation | IDAPython in a managed **idalib** worker | `ida_hexrays`, `idaapi`/`idautils`, `ida-domain` when useful; stdlib `ast`, `hashlib`, `json`. A self-contained source-backed `RemoteModule(codec="json")` imports IDA modules only inside its worker. The pure rule validator/interpreter remains testable without IDA. Store IDA findings and triage in the managed IDB. |
| External RE provider adapters | Python MCP client + vetted Ghidra/radare2 MCPs | Direct dependency on the official `mcp` Python client SDK; only configured stdio or authenticated loopback endpoints, pinned/tested provider tool schemas and bounded typed results. Run preparation and supported rules through backend-specific adapters, not pseudocode-text guessing or unrestricted provider commands. |
| Shared catalog and OMP board | Python stdlib `sqlite3`; TypeScript OMP extension | Per-target SQLite catalog for preparation candidates, reviewed proposals, fallback findings, and linked-triage journal; IDB netnode remains authoritative for unlinked IDA findings. OMP `tool_result`/`ctx.ui.setWidget` presents cached views and human review controls, not another storage or MCP client. |
| Packaging / tests | `pyproject.toml` + `uv.lock`; `pytest` and Bun tests (dev) | Start from `ida-mcp==20260924.0.3`, `ida-nexus==0.13.0`, `ida-domain==0.5.1`; pin a tested MCP client SDK and concrete Ghidra/radare2 provider versions during integration. Re-lock and smoke-test both adapters before upgrades; baseline versions are not a promise of future compatibility. |

Python layout: `src/vulfi_mcp/server.py` registers tools and coordinates adapters; `src/vulfi_mcp/ida_runtime.py` is source-backed IDA interpreter/scanner/netnode code; `src/vulfi_mcp/prepare.py` owns bounded pass/evidence contracts and proposal validation; `src/vulfi_mcp/providers/{ghidra,r2}.py` own fixed provider tool mappings; `src/vulfi_mcp/catalog.py` owns SQLite catalog and linked-triage journal; `src/vulfi_mcp/data/{rules,prototypes}.json` pins VulFi inputs. `omp/extension.ts` presents triage and operator review; `vulfi-mcp review` and `vulfi-mcp link` support review without OMP. `tests/` separates pure contracts, licensed IDA integration, live provider integrations, and OMP tests. `pyproject.toml` exposes `vulfi-mcp = "vulfi_mcp.server:main"`. Preserve applicable MIT dependency notices and Apache-2.0 attribution for copied VulFi code/data.

Data flow: `agent -> OMP MCP bridge -> vulfi-mcp @tool -> prepare -> {IDA Nexus worker | vetted Ghidra/r2 MCP client session} -> backend-tagged evidence -> supported rule evaluation -> {IDA netnode | SQLite} -> JSON-native response -> OMP board`. `vulfi_scan` reuses a matching preparation revision or runs preparation first; different backends can supply different passes/rules, with explicit gaps. The stock six IDA tools share the VulFi MCP process, but their MCP-local `instance_id` is not a VulFi parameter. Per-IDB changes use one remote operation followed by `handle.save_database()`; SQLite writes use transactions. An IDB save failure or external project write failure is not represented as durable. IDA `SetType` changes are not rollbackable inside a worker; managed artifacts and checkpoints contain them. Cross-store linked assessments have no atomic transaction and use a durable synchronization journal described below.

First integration gate: run the entry point without an IDA GUI provider; verify six official + **seven** VulFi tools, `backend="idalib"` for a supported fixture, nested agent-authored rule JSON through ZeroMCP/OMP, and source-backed execution in an existing worker. Independently connect to pinned Ghidra/radare2 MCP providers, preflight required tool schemas, prepare a real fixture, and report unsupported rules when IDA decompilation is unavailable. Use isolated `IDAUSR`/test environments rather than removing the operator's installed plugins. The fuller preparation and link/sync gates appear below and in the preparation specification.

## Agent-facing contract

- `vulfi_rule_template() -> RuleTemplate`: return the exact `Rule` object schema, valid example rules, supported predicates/operators, and safety/coverage notes in one response; no IDB required. Agent-generated rules use this template, not a Python code tool.
- `vulfi_prepare(path: str, backend: str = "auto", passes: list[str] | None = None) -> PreparationResult`: run bounded string/function/structure/pointer-table discovery on managed analysis artifacts, using IDA or configured external MCP providers per pass; return `analysis_id`, `preparation_revision`, source identity, per-pass backend/coverage, applied changes, candidate counts, warnings, and managed artifact paths. `backend` is `auto|ida|ghidra|r2`; invalid/empty pass lists fail before mutation. IDB-only input cannot use external providers without the original binary. See the [pass and safety contract](2026-09-29-vulfi-re-preparation-design.md).
- `vulfi_preparation(path: str, analysis_id: str | None = None, offset: int = 0, limit: int = 100) -> PreparationPage`: page candidate/evidence/review state without rerunning passes; `0 <= offset`, `1 <= limit <= 200`. A missing catalog is reported as unavailable, not as no candidates.
- `vulfi_propose_recovery(path: str, analysis_id: str, proposals: list[RecoveryProposal]) -> ProposalResult`: validate and store evidence-linked suggestions from the agent/LLM without modifying backend analysis. Only an operator-driven OMP review or local `vulfi-mcp review` command can approve and apply named proposals after revalidation on the current managed artifact revision.
- `vulfi_scan(path: str, rules: list[Rule] | None = None, scan_name: str = "agent", backend: str = "auto", analysis_id: str | None = None) -> ScanResult`: `None` runs 24 stock rules in scope `default`; a nonempty list runs only supplied rules in scope `custom:<scan_name>`. Validate all rules before preparation or any IDB/SQLite mutation; `[]` is an error. Reuse a matching preparation revision or run `vulfi_prepare` first. Select IDA, Ghidra, or r2 **per rule** only when the adapter can provide the rule's structured evidence; report `{rule_index, backend, state: evaluated|unsupported|failed, reason}` for every rule. Return `path`, optional managed `idb_path`, `binary_sha256` when known, `analysis_id`, `preparation_revision`, the first 100 findings from this scope, `scope_total`, `target_total`, per-backend and aggregate `status_counts`, `scope_health`, `coverage`, and warnings. `coverage="complete"` requires all selected rules and eligible call sites to be evaluated; no supported backend yields `partial`, never a clean verdict. Rescans affect only the selected scope and backend; matching IDs retain assessment.
- `vulfi_findings(path: str, binary_path: str | None = None, offset: int = 0, limit: int = 100) -> FindingsPage`: retrieve stored rows without rescanning; `0 <= offset`, `1 <= limit <= 200`. A raw-binary path permits aggregation with its registered managed IDB; an IDB path alone returns only IDA rows until `binary_path` identifies the original bytes. Return backend/store health, linked synchronization state, `target_total`, per-backend/aggregate status counts, and paged rows sorted by verified address-space/location and finding ID. Never report an unavailable store as an empty store or create an IDB just to page results.
- `vulfi_triage(path: str, finding_id: str, status: str, rationale: str, binary_path: str | None = None) -> TriageResult`: set exactly `Not Checked|False Positive|Suspicious|Vulnerable` with nonempty rationale, assessed time, and store-specific revision. Reject unknown IDs. Unlinked findings update only their own authority; a reviewer-linked IDA/fallback pair updates the versioned linked decision and mirrors both stores, returning `sync_state` and both findings only after a confirmed save. Offline linked edits fail closed; independent rule/call-site assessments remain distinct.

`Finding` includes globally unique `id`, `backend` (`ida|ghidra|r2`), `source` (`default|custom:<scan_name>`), binary identity when available, rule index/digest/name, function name, containing function, address space, hexadecimal address (and verified relative address when derivable), occurrence ordinal, `priority` (`High|Medium|Low|Info`), `status`, `rationale`, `assessed_at`, `last_seen_scan_id`, evidence, optional `link_id`/`link_revision`, and freshness. An ID joins backend, scan scope, rule index, canonical-rule-JSON SHA-256, address space, address, and deterministic occurrence ordinal; IDA-only input without original bytes is scoped to its managed IDB. Numeric addresses from different backends never imply identical call sites. Rule changes or decompiler expression reordering may orphan assessments/links; require review before reattachment. Pagination is not a snapshot across rescans.

## Analysis semantics

Ship the 24 stock rules and needed prototypes from Accenture/VulFi at commit `0bb7fdf8ccb906600cc209c35daf05774172acc8`; preserve Apache-2.0 attribution/license when porting code/data. Stock and agent-authored rules use `Rule = {name: str, function_names: list[str], wrappers: bool, mark_if: {High: str, Medium: str, Low: str}}`. Priority evaluates those branches in order. A **verified** empty argument list may produce `Info`; unavailable argument recovery produces `unsupported` or `partial`, never an `Info` finding or a clean negative. Reproduce name matching, call xrefs, argument extraction, `Param` and `FunctionCall` predicates, one-level wrapper discovery, array-index and loop rules on capable backends. Preserve stock outcomes on IDA fixtures; documented defects (invalid shipped template, duplicate-name dedup collision, unchecked ASCII encoding) need not be reproduced. Do not claim interprocedural taint analysis or all-24-rule parity for external MCPs.

**Agent-authored expressions are untrusted input.** `mark_if` uses a restricted, VulFi-shaped expression language, never Python `eval` or `exec`. Parse the expression and interpret only approved boolean/arithmetic/comparison/index/list/list-comprehension AST nodes, literal values, `param[i]`, `param_count`, `function_call`, the stock `Param`/`FunctionCall` predicates, bounded `any`/`len`/`range`, and the string operations used by stock rules (`lower`, `split`, `startswith`). Whitelist receiver types and method names, not arbitrary attribute access; reject imports, dunder access, arbitrary callables and objects, mutation, and unsupported AST nodes with a rule-indexed error. Bounds apply to expression size and comprehension iteration. All 24 bundled rules must validate under this **same** interpreter, so default/custom rules cannot take different security paths. The template tool must demonstrate both a stock-compatible predicate and a custom one.

Rule definitions and per-rule coverage from complete **or partial** scans persist with backend-tagged findings so an agent can inspect which rules actually ran after restart. Malformed rules fail before preparation opens or modifies an analysis artifact. Missing decompilation, provider capabilities, or extraction evidence reports reduced coverage rather than invented negatives.

Preparation may apply validated function/type changes only in managed analysis artifacts, with a checkpoint and pass provenance. A stock IDA scan may call `SetType` when a prototype is needed for argument recovery; disclose this mutation and preserve the managed-IDB-only boundary. Read, pagination, and triage operations never apply prototypes. Cancellation and provider/worker failures release leases/sessions without replacing a completed scope with a falsely clean result.

### Backend capability and origin rules

`auto` prioritizes IDA evidence where its decompiler/disassembler supports the rule, then a configured Ghidra MCP, then a configured radare2 MCP. Run IDA disassembly-only rules even if its decompiler is absent; choose another provider for rules requiring unsupported evidence. Provider adapters are **not** dynamic translations of an arbitrary MCP tool list: each names allowlisted provider operations, validates `list_tools` input/output schemas and binary identity, bounds result sizes/time, and converts only justified observations into typed strings, functions, call sites, arguments, references, and loop/array facts. A decompiled C text response alone cannot satisfy a structural `Param` or loop predicate. If no provider supplies equivalent facts, mark that rule/call-site unsupported with a reason. Provider-specific findings remain distinct; a same-address pair becomes linkable only after verified original-binary identity, rule digest, address-space mapping, and operator review.

The official [MCP Python client](https://py.sdk.modelcontextprotocol.io/v1/client/) supports `ClientSession` over stdio and HTTP. Configure exact approved executable/args or authenticated loopback endpoint outside tool inputs, never launch or proxy arbitrary commands from an agent, and do not enable provider script/debug/raw-command tools by default. A remote endpoint requires explicit authentication and a verified local-to-provider binary path map; failures in that mapping disable its pass/rule rather than scanning a different binary. Reference adapters target a pinned [headless-capable Ghidra MCP](https://github.com/bethington/ghidra-mcp) and [radareorg/radare2-mcp](https://github.com/radareorg/radare2-mcp); actual provider releases/tool schemas become supported only after the real fixture gate. Other MCP servers require their own adapter and gate.

## Persistence and interoperability

Use two explicit authorities: the **managed IDB netnode** stores IDA-produced rules, findings, and unlinked assessments; a per-original-binary **SQLite** catalog outside the public repository stores preparation evidence/proposals, fallback findings/assessments, and the journal coordinating reviewer-linked assessments. A linked decision is authoritative in the catalog and mirrored with revisions into the IDB. The IDB retains its own findings when the catalog is unavailable; it must not imply that missing external rows equal zero. Moving the managed IDB alone preserves IDA findings/assessments but not fallback history or active link synchronization. The legacy VulFi `vulfi_data` netnode is untouched; migration of old chooser rows is separate. Neither a source binary nor a user-supplied original IDB is modified by VulFi preparation.

### Managed IDB record (schema version 2)

The IDA authority is one UTF-8 JSON blob in netnode `vulfi_mcp.v2`, blob `(index=1, tag="S")`. An IDA scan or unlinked triage reads/modifies/writes within one remote IDA operation, then calls `handle.save_database()` and reports failures; no IDA netnode transaction is assumed. Unknown future schema versions are rejected rather than overwritten. The managed IDB includes a bounded preparation summary so its own rule context remains understandable without SQLite. This is a new design-stage format, not a migration path from an already shipped `v1` implementation:

```json
{
  "schema_version": 2,
  "managed_idb_id": "opaque-stable-uuid",
  "preparation": {
    "analysis_id": "opaque-uuid",
    "revision": 1,
    "coverage": {"strings": "complete", "functions": "complete", "structures": "complete", "pointer_tables": "complete"},
    "catalog_key": "<target-sha256>"
  },
  "scopes": {
    "default": {
      "rules": [{"name": "Buffer Overflow", "function_names": ["strcpy"], "wrappers": false, "mark_if": {"High": "not param[1].is_constant()", "Medium": "False", "Low": "False"}}],
      "scan_id": "opaque-uuid",
      "scanned_at": "2026-09-29T00:00:00Z",
      "coverage": "complete",
      "rule_coverage": {"0": {"backend": "ida", "state": "evaluated", "reason": null}},
      "warnings": [],
      "findings": {
        "ida:default:0:<sha256>:image:0x401234:0": {
          "id": "ida:default:0:<sha256>:image:0x401234:0",
          "backend": "ida",
          "source": "default",
          "rule_index": 0,
          "rule_digest": "<sha256>",
          "rule_name": "Buffer Overflow",
          "function_name": "strcpy",
          "found_in": "main",
          "address_space": "image",
          "address": "0x401234",
          "occurrence": 0,
          "priority": "High",
          "status": "Not Checked",
          "rationale": "",
          "assessed_at": null,
          "triage_revision": 0,
          "link_id": null,
          "link_revision": null,
          "last_seen_scan_id": "opaque-uuid",
          "evidence": {"matched_branch": "High", "expression": "not param[1].is_constant()", "analysis_mode": "ctree"}
        }
      }
    }
  }
}
```

The example is illustrative, not a fixture guarantee. Scope keys are `default` and `custom:<scan_name>`; validate `scan_name` as a nonempty ASCII identifier without colon or path separators. A rule digest is SHA-256 of canonical UTF-8 JSON (`sort_keys=True`, compact separators, `ensure_ascii=False`). IDs include backend, scope, zero-based rule index, full rule digest, address space, lowercase hexadecimal address, and occurrence ordinal; duplicate-name rules do not collide. An external ID additionally belongs to the original-binary SHA-256 namespace; IDA-only input without binary bytes belongs to its managed IDB namespace. Changing a rule or ctree occurrence ordering can orphan an assessment and pause a linked pair; never attach the previous assessment to an unrelated call. Times are UTC ISO-8601; `assessed_at=null` and `rationale=""` mean not yet assessed. Evidence is bounded JSON, not raw IDA objects.

Each backend stores its own `default`/`custom:<scan_name>` scopes. On a complete scan of one backend/scope, replace only that scope's findings and preserve triage by exact ID. On partial rule/call-site coverage, merge observed rows, keep prior rows marked stale via `last_seen_scan_id`, and record per-rule `evaluated|unsupported|failed` reasons. A cancelled scan does not commit a falsely complete scope; a later complete scan can retire stale rows. Rescanning another backend/scope cannot delete these rows. A stale, missing, or changed linked finding pauses synchronization until reviewed again; do not mirror to a newly similar address.

Responses include per-backend `scope_health`, preparation/rule coverage, store availability, linked `sync_state`, and `status_counts` by backend plus an aggregate. Counts include stale findings but label them; the aggregate counts findings, **not deduplicated vulnerabilities**, so linked pairs still contribute two rows. `target_total` covers available stores only and has an explicit completeness indicator; a missing SQLite store is `unavailable`, not zero. `path` is the canonical input path and optional `idb_path` is the managed IDB path from `DatabaseHandle.instance.idb_path` (not `db.path`, which may name the source executable). An IDB-only request cannot join external results without supplying/verifying the original binary. Pagination sorts by verified address space/location, backend, then ID; OMP's session cache is never an authority.

### SQLite catalog and finding links

Use a schema-versioned SQLite catalog under operator-configured application data, never by default in a source tree or binary directory. Key it by original-binary SHA-256 when available; for IDB-only input use a provisional stable managed-IDB UUID stored in the netnode, with `source_sha256=null`. Tables: `targets` (identity and optional source hash), `analyses` (provider/artifact identity, capability fingerprint, preparation revision), `passes` (backend/range/coverage), `candidates` and `proposals` (evidence, approval state), `external_scopes` and `external_findings` (rules, coverage, triage), `links` (paired IDs, reviewed identity/mapping, canonical linked decision, revision/state), and `sync_events` (durable replay journal). Enforce foreign keys and unique backend/scope/finding IDs; perform per-scope updates and unlinked external triage transactionally. The catalog never overwrites the IDA netnode or copies IDA triage as a substitute authority. No original binary bytes are stored. IDB-only preparation/candidate review works in its provisional catalog, but fallback, catalog joining, and finding links require the original binary and a verified IDB-to-binary fingerprint or segment-byte association; never attach an arbitrary supplied binary to the IDB on path/name alone.

The operator creates a link through OMP review or local `vulfi-mcp link`, not through an ordinary agent-callable MCP mutation. Require the original binary hash to match both analyses, matching full rule digest, verified address-space mapping to the **same call site**, non-stale finding IDs, and a reviewer-chosen initial assessment. The link records both IDs, mapping evidence, chosen source, canonical status/rationale/time, and expected triage revisions. Numeric equality or a matching function name alone never creates a link. Unlinked findings remain independently assessed; reviewed links keep both backend findings and their evidence visible.

For linked triage, SQLite records the next versioned decision and a `pending` event in a short transaction; the IDA adapter compares its expected netnode revision, writes the mirror in one IDA operation, and saves the managed IDB; SQLite then marks the event `complete` after verifying both revisions. The external row and canonical link decision are updated with the pending event, so readers must expose `pending`, not claim the pair is synchronized until completion. A repeat request with the same link/event ID is idempotent. On restart, replay a pending event when IDA still has the expected previous revision, or finalize it when the IDB already has the intended revision; an unexpected revision yields `conflict` without last-write-wins. Serialize link updates per target using the SQLite link revision; no long SQLite transaction is held across a remote IDA save. Failure after either write returns non-complete state and retriable provenance, never a false success.

If SQLite is unavailable, the IDA mirror remains readable but linked edits fail closed; unlinked IDA triage still works. A rescan that drops/changes either exact linked finding or marks it stale moves the link to `paused`; operator review is required to relink. A conflicting out-of-band update moves it to `conflict`; the reviewer chooses which assessment wins, and a new guarded event synchronizes both. These states and the last confirmed revision appear in MCP results and the OMP board. There is no atomic commit spanning IDA and SQLite, and no automatic status propagation to an unreviewed pair.

## OMP triage board

The OMP extension consumes only validated VulFi tool results and shows a separate preparation/triage board: candidate counts and pass coverage, loaded findings by backend and address space, per-backend and aggregate `Not Checked|False Positive|Suspicious|Vulnerable` counts, stale badges, and `pending|conflict|paused` link state. A reviewed link can group two backend rows without claiming one unique vulnerability or hiding their evidence. `vulfi_scan` returns at most 100 findings for its selected scope, and `vulfi_findings`/`vulfi_preparation` page further rows; show `loaded / target_total` with unavailable-store warnings instead of pretending all rows are loaded. An OMP human-facing command reviews evidence and invokes the fixed local review/link CLI only after an operator decision; ordinary VulFi MCP tools can propose but cannot approve. A shell-capable agent with operator OS privileges could run that CLI, so hard human separation requires distinct review-command credentials. OMP's native `todo` remains task/phase state: never call `todo.init` or create a todo item per finding.

Use documented OMP extension APIs (`tool_result`, `ctx.ui.setWidget`, commands/custom UI). Verify MCP server origin and response schema before accepting a result; unrelated providers cannot alter the board. The board stores only a session-local view, not netnode/SQLite authority, and shows its last refresh time. After external IDB/catalog changes, the agent calls `vulfi_findings` or `vulfi_preparation` to refresh. It does not start an MCP client or assume OMP `ctx.invokeTool` can page arbitrary MCP tools. Without OMP, the agent-facing MCP tools and local operator review CLI still work.

## Verification and release gate

Unit tests validate the restricted interpreter against all 24 stock expressions and custom examples; reject dangerous rules **before** preparation/DB changes. Cover schema/priority precedence, duplicate-name and call-site identity, wrappers/array/loop detectors, `Info` only for verified empty arguments, malformed rules, scoped complete/partial rescan behavior, Unicode rationale, per-backend coverage, stale IDs, and unavailable store/provider results. Fixture tests must assert specific observable recoveries and assessment transitions, never mock echoes or incidental tool forwarding.

A real headless IDA integration lists six stock + seven VulFi tools, opens a compiled fixture with `backend="idalib"`, prepares unmarked strings/function/structure/pointer evidence, evaluates stock and custom rules, and saves/reopens the managed IDB with its independent IDA findings and preparation summary. The supplied original artifact remains unchanged. On decompiler-unavailable input, connect to an explicitly configured real Ghidra/radare2 MCP, validate tools/schema and binary identity, exercise supported passes/rules, and enumerate unsupported rules and failed ranges; no zero-finding result may imply complete coverage. Missing provider, malformed response, timeout, and path-map mismatch must not erase earlier findings. Run the provider gate independently for every backend/version claimed supported; do not advertise untested parity.

With matching fixtures scanned by IDA and a fallback backend, require reviewer-created links to verify original-binary hash, full rule digest, address-space mapping, and live findings. Triage from either backend must update both copies and survive IDB/catalog reload. Interrupt after the pending SQLite event and after the IDB save separately; verify replay, idempotence, visible `pending`, offline linked-edit refusal, conflict review, and pause after a stale/rescanned member.
