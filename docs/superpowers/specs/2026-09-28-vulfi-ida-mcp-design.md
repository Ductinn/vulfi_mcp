# VulFi tools in the official IDA MCP — design

## Purpose and acceptance

Expose VulFi's vulnerability **analysis, agent-authored rule scanning, and per-finding triage** as discoverable MCP tools to an LLM agent using Hex-Rays' official IDA MCP. Keep one MCP process and the six stock IDA tools; do not fork `ida-mcp`, start a second MCP server, or install/use an IDA GUI plugin. A user can request a rule template, run all 24 stock rules or supply a custom rule, inspect findings, and record an assessment for each distinct rule/call-site finding. Findings and assessments survive closing and reopening the headless IDB. An OMP extension presents a todo-like triage board without replacing OMP's built-in task list. Wrapper, loop, and array rules run where the headless IDA license provides Hex-Rays decompilation.

This is a new design-stage project with no product code yet. IDA GUI attachment, GUI chooser/menu reimplementation, migration of legacy VulFi netnode rows, arbitrary Python execution from rule input, and a general taint-analysis engine are outside scope. Existing VulFi GUI code is not the backend.

## Runtime architecture

A `vulfi-mcp` entry point imports the documented `tool` and `serve_stdio` API from `ida_mcp.mcp`, registers VulFi tools and serves that **same** process-wide MCP server. The agent config points to `vulfi-mcp` instead of `ida-mcp stdio`; the six stock tools stay visible. The tool implementation uses only exported `ida_nexus` APIs (`DatabaseHandle.open`, `RemoteModule` or `remote_ida`) to run its engine in IDA. It does not access `ida_mcp.mcp.DATABASE_MANAGER`, derive an IDA runtime from stock MCP-local `instance_id`, monkeypatch stock tools, or call an MCP server over HTTP. Each VulFi tool accepts an explicit local `path` (binary or IDB), and Nexus reuses/spawns a headless `idalib` worker; its lease is released after each tool call. No GUI plugin is installed by this project. All data crossing Nexus/MCP boundaries is JSON-native.

Engine logic is a separate source-backed Python module executed inside IDA. Its code is not an `execute_python` string generated by an agent. Use the IDAPython decompiler/ctree and disassembly APIs needed by VulFi; `ida-domain` is available alongside them. No imported VulFi GUI objects or wait-box, chooser, popup, or modal calls in the scan path.

Runtime support: IDA >=9.4 with activated idalib and a license that supports the relevant decompiler, Python >=3.11, one locked/tested resolution of `ida-mcp`, `ida-nexus`, and `ida-domain`. Releasing/upgrading changes the lockfile only after integration checks; no promise of compatibility with arbitrary future versions. The supported deployment has no Nexus/IDA-MCP GUI provider plugin installed or enabled: if one is present, Nexus may prefer its GUI instance and headless-only behavior is not guaranteed. When another official MCP process uses a compatible headless worker, Nexus attaches to it; an incompatible peer is surfaced as an error. If an unregistered IDA GUI holds the same IDB lock, report `DatabaseBusyError` and ask the operator to save/close that GUI database; do not attempt to bypass the lock or copy a stale IDB.

### Local idalib feasibility check (2026-09-28)

The existing official IDA MCP was smoke-tested against a disposable copy of `/bin/true`, not a user IDB. `open_database` reported `backend="idalib"` and `recovery="none"`; the worker ran Python 3.14.3 and ida-domain 0.5.1. IDA enumerated 126 x86-64 functions through both `db.functions.get_all()` and `idautils.Functions()`, `ida_hexrays.init_hexrays_plugin()` returned `True`, and `db.pseudocode.decompile()` returned pseudocode for `.init_proc`. Saving `.i64`, closing its lease, reopening that IDB in an idalib worker, and decompiling again succeeded. Both leases were released and the temporary files removed.

This proves headless import, analysis, decompilation, and IDB save/reopen on this machine for **ELF x86-64 only**. A GUI-provider plugin is installed locally but no GUI database was attached during the test; this check does **not** prove startup with the GUI provider uninstalled, other architectures' decompiler availability, custom VulFi tools, or the OMP extension. The release-gate end-to-end checks below still have to prove those behaviors.

## Technology and component boundaries

| Component | Language / runtime | Dependency and ownership |
|---|---|---|
| MCP adapter (`vulfi-mcp` CLI) | Python >=3.11 | Direct dependency on the **official** `ida-mcp` for `@tool` and `serve_stdio`, and `ida-nexus` for `DatabaseHandle`/`RemoteModule`; `ida-domain` comes through Nexus but is locked and tested explicitly. No second MCP implementation or HTTP service. |
| Analysis in IDA | IDAPython in a managed **idalib** worker | `ida_hexrays`, `idaapi`/`idautils`, `ida-domain` when useful; Python stdlib `ast`, `hashlib`, `json`. Send a self-contained, source-backed `RemoteModule` with `codec="json"` so a worker started by another compatible Nexus client need not have our Python package installed. The remote source imports IDA modules only while executing inside IDA; its pure rule validator/interpreter is also importable in unit tests outside IDA. |
| OMP triage board | TypeScript, OMP extension runtime | Use documented `tool_result` hooks and `ctx.ui.setWidget`; no second MCP client, no Vue/React/server, and no dependency on native `todo` internals. OMP is an optional UI dependency, not a prerequisite for the Python MCP tools. |
| Packaging / tests | `pyproject.toml` + `uv.lock`; `pytest` (dev), Bun test for the extension (dev) | Pin an **exact tested set** starting from `ida-mcp==20260924.0.3`, `ida-nexus==0.13.0`, `ida-domain==0.5.1`; lock transitive dependencies. Re-lock and run compatibility tests before accepting updates. These are baseline versions, not a promise of future compatibility. |

Python layout: `src/vulfi_mcp/server.py` owns tool registration, validation dispatch, Nexus leases, and JSON output; `src/vulfi_mcp/ida_runtime.py` is the self-contained source-backed interpreter/scanner/netnode code loaded into IDA; `src/vulfi_mcp/data/{rules,prototypes}.json` pins VulFi's stock inputs; `omp/extension.ts` owns presentation only. `tests/` separates pure rule/scan-contract tests from licensed headless IDA integration and OMP extension tests. `pyproject.toml` exposes `vulfi-mcp = "vulfi_mcp.server:main"`. Both MIT dependency notices and Apache-2.0 attribution for copied VulFi code/data ship with the package.

Data flow: `agent -> OMP MCP bridge -> vulfi-mcp @tool -> DatabaseHandle.open(path) -> RemoteModule.function(handle, JSON arguments) -> IDA runtime (single IDB operation) -> JSON-native response -> OMP tool_result -> triage board`. The stock six IDA tools live in this same MCP process, but their MCP-local `instance_id` is **not** a VulFi tool parameter; VulFi takes `path` and has its own short-lived Nexus lease. Per-tool mutations use one remote read/modify/write operation to avoid losing a concurrent scan/triage update. The MCP adapter calls `handle.save_database()` after successful IDB mutation and always closes its own lease; a save failure is reported, not misrepresented as durable. IDA `SetType` mutations made during a failed scan cannot be rolled back automatically.

First integration gate: start the custom entry point with a disposable binary and no GUI provider; verify all six official + four VulFi tools appear, `backend="idalib"`, a nested agent-authored `Rule` survives ZeroMCP/OMP JSON-schema normalization, `RemoteModule` executes against an existing worker, and OMP receives the expected result origin and JSON shape. A local GUI-provider installation must not be removed from the user's machine just to run this gate; use an isolated `IDAUSR`/test environment.

## Agent-facing contract

- `vulfi_rule_template() -> RuleTemplate`: return the exact `Rule` object schema, valid example rules, supported predicates/operators, and safety/coverage notes in one response; no IDB required. Agent-generated rules use this template, not a Python code tool.
- `vulfi_scan(path: str, rules: list[Rule] | None = None, scan_name: str = "agent") -> ScanResult`: `None` runs the 24 stock rules in scope `default`; a non-empty list runs **only** supplied rules in scope `custom:<scan_name>`. Separate names keep independent custom scans; rescanning a named scope replaces only that scope. Validate every rule before any IDB mutation; `[]` is an error. Return `{path, source, analysis_mode, findings, scope_total, database_total, status_counts, warnings}`: `path` is the canonical IDB path, `findings` contains the first 100 rows **from the scanned scope**, `scope_total` counts that scope, and `database_total`/`status_counts` cover **all** findings in this database. `vulfi_findings` pages through the full database. Rescans preserve assessments for matching IDs. Warnings identify incomplete coverage (decompiler-unavailable detectors, individual call failures). Do **not** mark `read_only`: applying prototypes and persisting findings mutate IDB state.
- `vulfi_findings(path: str, offset: int = 0, limit: int = 100) -> FindingsPage`: retrieve all stored findings without rescanning; return `{path, findings, offset, total, status_counts}` with `0 <= offset` and `1 <= limit <= 200`; sort by numeric address then finding ID. `path` is the canonical IDB path, `total`/`status_counts` cover the full database. Do not annotate `read_only`: opening a raw binary path can create an analyzed IDB.
- `vulfi_triage(path: str, finding_id: str, status: str, rationale: str) -> TriageResult`: set status to exactly `Not Checked`, `False Positive`, `Suspicious`, or `Vulnerable`, persist a non-empty rationale and update time; return `{path, finding, database_total, status_counts}` for an immediate board update. An unknown ID is an error, not a new finding. Each rule at one address is assessed independently; the board groups findings by call address without collapsing their assessments.

`Finding` contains `id`, `source` (`default|custom:<scan_name>`), rule identity, `rule_name`, `function_name`, `found_in`, `address` as a hex string, `priority` (`High|Medium|Low|Info`), `status`, `rationale`, `assessed_at` (nullable until assessed), and evidence including the matched rule expression and analysis mode. IDs distinguish scan scope, rule index, canonical-rule-JSON SHA-256 prefix, hexadecimal address, and an occurrence ordinal for multiple expressions at one address. A change to a rule or decompiler expression ordering may invalidate an old ID and its assessment. Pagination is sorted but not a snapshot: a rescan between page requests may change offsets.

## Analysis semantics

Ship the 24 built-in rules and the needed prototypes from Accenture/VulFi at commit `0bb7fdf8ccb906600cc209c35daf05774172acc8`; preserve Apache-2.0 attribution/license when porting code/data. Both stock and agent-authored rules use `Rule = {name: str, function_names: list[str], wrappers: bool, mark_if: {High: str, Medium: str, Low: str}}`. Priority evaluates branches in that order; an empty/unavailable argument list produces `Info`, and no truthy branch produces no finding. Reproduce name matching, call xrefs, argument extraction, `Param` and `FunctionCall` predicates, one-level wrapper discovery, array-index and loop rules. Preserve observable stock-rule outcomes on fixture binaries; documented defects (invalid shipped template, duplicate-name dedup collision, unchecked ASCII encoding) need not be reproduced. Do not claim interprocedural taint analysis.

**Agent-authored expressions are untrusted input.** `mark_if` uses a restricted, VulFi-shaped expression language, never Python `eval` or `exec`. Parse the expression and interpret only approved boolean/arithmetic/comparison/index/list/list-comprehension AST nodes, literal values, `param[i]`, `param_count`, `function_call`, the stock `Param`/`FunctionCall` predicates, bounded `any`/`len`/`range`, and the string operations used by stock rules (`lower`, `split`, `startswith`). Whitelist receiver types and method names, not arbitrary attribute access; reject imports, dunder access, arbitrary callables and objects, mutation, and unsupported AST nodes with a rule-indexed error. Bounds apply to expression size and comprehension iteration. All 24 bundled rules must validate under this **same** interpreter, so default/custom rules cannot take different security paths. The template tool must demonstrate both a stock-compatible predicate and a custom one.

Rule definitions from a complete **or partial** scan are stored with their findings (versioned, canonical JSON) so an agent can inspect which rule produced a triaged result after restart. A malformed rule fails before the scan opens or modifies the IDB; decompiler absence reports reduced coverage rather than invented negatives.

A scan may call IDA `SetType` when a stock prototype is needed for argument recovery; this mutates the IDB and must be explicit in tool metadata and documentation. Read/triage operations must not apply prototypes. Scanner cancellation and operation failures must close the Nexus lease without producing a falsely complete finding set.

## Persistence and interoperability

Use a dedicated, versioned IDB netnode namespace for VulFi MCP findings, rule definitions, and triage; retain findings between MCP sessions and save the IDB after successful mutation. No JSON sidecar is required. Use UTF-8-safe JSON persistence and write a complete replacement blob only after producing a complete or explicitly partial result, without claiming transactional guarantees from IDA netnodes. Stock and custom scan scopes cannot delete each other's findings. The legacy `vulfi_data` netnode used by VulFi's chooser is not overwritten; the legacy chooser does not read the new annotations. If the operator needs old annotations, migration is a separate explicit request. Within the active scope, only a complete scan can retire findings no longer detected; partial scans retain older rows as potentially stale.

### IDB record format (schema version 1)

One UTF-8 JSON blob in netnode `vulfi_mcp.v1`, blob `(index=1, tag="S")`, is the source of truth. A scan or triage operation performs **read -> modify -> write within one remote IDA operation**; then the adapter requests `handle.save_database()`. The blob is versioned to reject an unknown newer schema rather than overwrite it. The per-IDB structure is:

```json
{
  "schema_version": 1,
  "scopes": {
    "default": {
      "rules": [{"name": "Buffer Overflow", "function_names": ["strcpy"], "wrappers": false, "mark_if": {"High": "not param[1].is_constant()", "Medium": "False", "Low": "False"}}],
      "scan_id": "opaque-uuid",
      "scanned_at": "2026-09-29T00:00:00Z",
      "coverage": "complete",
      "warnings": [],
      "findings": {
        "default:0:<sha256>:0x401234:0": {
          "id": "default:0:<sha256>:0x401234:0",
          "source": "default",
          "rule_index": 0,
          "rule_digest": "<sha256>",
          "rule_name": "Buffer Overflow",
          "function_name": "strcpy",
          "found_in": "main",
          "address": "0x401234",
          "occurrence": 0,
          "priority": "High",
          "status": "Not Checked",
          "rationale": "",
          "assessed_at": null,
          "last_seen_scan_id": "opaque-uuid",
          "evidence": {"matched_branch": "High", "expression": "not param[1].is_constant()", "analysis_mode": "ctree"}
        }
      }
    }
  }
}
```

The example rule/addresses are **illustrative**, not a promised finding for a fixture. Scope keys are `default` and `custom:<scan_name>`; validate `scan_name` as a non-empty ASCII identifier without colon or path separators. A rule's digest is SHA-256 of its canonical UTF-8 JSON (`sort_keys=True`, compact separators, `ensure_ascii=False`). IDs join scope, zero-based rule index, full digest, lowercase hexadecimal address, and deterministic occurrence ordinal; duplicate-name rules therefore do not collide. A different rule definition or reordering of multiple ctree expressions at the same address changes the ID and may orphan its old assessment; do not silently attach that assessment to another call. `assessed_at` and `scanned_at` are UTC ISO-8601 strings; `assessed_at=null` and `rationale=""` mean no assessment yet. `evidence` is JSON-native and contains the matched condition/analysis mode, never raw SWIG or IDA objects.

On a **complete** rescan, replace findings in only the selected scope and carry `status`, `rationale`, and `assessed_at` forward by exact ID. On **partial** coverage (missing decompiler or a skipped call), merge newly observed findings into the same scope, retain prior rows, set `coverage="partial"` and record warnings. Use `last_seen_scan_id` to mark rows not reobserved in that partial scan as stale; neither the MCP nor OMP may present those rows as freshly verified. Cancellation or failure before a finished result does not replace the stored scope; a cancelled scan is not presented as a clean partial result. Failed validation happens **before** opening the IDB and does not write an IDB. The next complete scan can retire stale rows. Scans of another scope are untouched.

`vulfi_scan`, `vulfi_findings`, and `vulfi_triage` return `scope_health` (per-scope coverage/warnings) alongside their existing result fields, and `vulfi_scan` reports `coverage` for the selected scope. `status_counts` is recomputed from **all stored findings**; counts include retained stale rows, which the board marks separately. `path` in results is the canonical IDB file path from `DatabaseHandle.instance.idb_path`, not `db.path` (which can still name the original executable). Pagination sorts by integer address and full finding ID. OMP holds only a session-local cache of currently loaded rows; it neither writes this netnode nor acts as a second database.

## OMP triage board

The shipped OMP extension consumes VulFi MCP tool results and presents a separate, todo-like triage board: full-database counts by `Not Checked|False Positive|Suspicious|Vulnerable`, findings grouped by call address with priority/rule/status, and a paged view of **loaded** rows. `vulfi_scan` yields up to 100 findings in its scan scope; the agent fetches remaining/full-database pages through `vulfi_findings`, updating the board incrementally. The board shows `loaded / database_total` rather than pretending unloaded findings are visible. `vulfi_triage` updates the assessed row and aggregate counts immediately. OMP's native `todo` is task/phase state in one session, not an IDB finding database: do not call `todo.init`, create a todo task per finding, or use it as storage. IDB netnode data is the source of truth. The extension may cache a view in the session and restore it on resume; after external IDB changes, the agent calls `vulfi_findings` to refresh, and the board displays its last-refresh time rather than claiming live synchronization.

Use documented OMP extension APIs (`tool_result` interception, `ctx.ui.setWidget`, command/custom UI for a paged view of loaded rows). Match MCP origin and JSON response schema before accepting results; unrelated IDA/MCP tools cannot alter the board. The extension does not start another MCP client/process and cannot autonomously page the server through OMP's `ctx.invokeTool` (which only delegates to a shadowed native tool). When OMP is absent, all MCP tools and persisted triage still work.

## Verification and release gate

Unit tests exercise all 24 stock expressions and example agent-authored expressions against the restricted interpreter, dangerous expressions being rejected **before** IDB changes, rule schema/priority precedence, name matching, duplicate-named rules, wrapper/array/loop detectors, per-argument predicates, per-rule/call assessment transitions, custom-vs-default scan isolation, rescan preservation, Unicode rationales, malformed rules, and decompiler-unavailable coverage. Tests use fixture binaries or plain Python stand-ins rather than checking source text/tool forwarding. An end-to-end test launches the custom MCP entry point **without a GUI or GUI provider plugin**, lists all six stock tools plus `vulfi_rule_template`, `vulfi_scan`, `vulfi_findings`, `vulfi_triage`, opens a compiled fixture through stock `open_database`, asserts `backend="idalib"`, runs stock and agent-authored rule scans, assesses two distinct call-site findings, saves/closes/reopens the IDB, and verifies both assessments and rule snapshots survive. A second scenario opens the fixture in an unregistered GUI and checks that an IDB lock conflict is surfaced without clobbering data, if GUI test setup is available. An OMP integration scenario verifies that scan/triage tool results update the separate board without changing native todos and that a findings refresh rebuilds the board after session resume. Run the integration against the locked dependency set and before accepting an `ida-mcp`/`ida-nexus` upgrade. Include Apache-2.0 attribution and short install/tool documentation.
